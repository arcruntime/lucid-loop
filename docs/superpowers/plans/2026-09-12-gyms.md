# Character and Live Gyms Implementation Plan

> **For agentic workers:** Use superpowers:subagent-driven-development to implement the backend task, with local Unity implementation and whole-change review.

**Goal:** Deliver two playable Unity gyms: offline nightclub navigation/conversation framing and live audio conversation through a secret-holding backend.

**Architecture:** Unity 6000.3.24f1 URP scenes share reusable primitive characters and UI. The offline scene uses baked NavMesh navigation and mouse/touch gesture classification. The live scene uses a native WebSocket connection to a bounded Node relay; only the relay accesses OpenAI GPT-Live.

**Tech Stack:** Unity 6.3 LTS, URP 17.3, osu-framework-unity-di pinned Git dependency, C#, Node 24, ws, OpenAI Live API.

**Spec:** `../specs/2026-09-12-character-gym-design.md`, `../specs/2026-09-12-live-conversation-gym-design.md`, amended by the user's approval: no SSO, project API key is a GitHub secret; build both gyms.

## Task 1: Live backend and deployment contract

Files: `server/package.json`, `server/src/*.mjs`, `server/test/*.test.mjs`, `server/README.md`, `server/Dockerfile`, `.github/workflows/gyms.yml`.

Interface: WebSocket `/live` accepts first message `{type:"gym.start",character:"maya",token:"..."}`; token is an optional local-only development omission, required for non-loopback deployments. Server emits `{type:"gym.status",status:"connecting"}` then forwards documented GPT-Live events. Client sends only `session.input_audio.append`, `session.input_audio.mute`, `session.input_audio.unmute`, `session.close`. PCM16 mono 24kHz. Server owns session.start, prompts, model, maximum duration, concurrency and all secrets. Reject other client event types. Health route returns readiness without secrets.

## Task 3: Unity live gym

Files: `Unity/Assets/Gyms/Runtime/Live/*.cs`, shared scene builder and UI.

Interface: serialized relay URL, runtime-only access token, character selection; relay protocol from Task 1. Never request or store an OpenAI key in Unity. ClientWebSocket receives JSON, dispatches main-thread state, streams microphone chunks and queues output PCM for audio playback. Audio thread consumes a bounded ring buffer; UI shows real connection state/transcripts/errors.
